# Домашнее задание к занятию "Базы данных, их типы" - Nikiforov Viktor

### Задание 1

Крупная строительная компания, которая также занимается проектированием и девелопментом, решила создать правильную архитектуру для работы с данными.
Ниже представлены задачи, которые необходимо решить для каждой предметной области.

Какие типы СУБД, на ваш взгляд, лучше всего подойдут для решения этих задач и почему?

## СУБД

### 1.1. Бюджетирование проектов с дальнейшим формированием финансовых аналитических отчётов и прогнозирования рисков. СУБД должна гарантировать целостность и чёткую структуру данных.

В данной ситуации лучше всего подойдёт реляционная SQL OLTP для первичных данных + хранилище/OLAP для аналитики.
SQL (OLTP): бюджетирование - это договоры, статьи затрат, сметы, права доступа, согласования.
Нужны ACID-транзакции, ссылочная целостность, строгая схема, контроль изменений.

OLAP: финансовык отчёты и прогнозирование рисков часто требуют тяжёлых агрегаций по периодам/объектам/подрядчикам.
Это удобнее и дешевле выполнять в колонночном хранилище.

Примеры:
  - OLTP: PostgreSQL / MS SQL / Oracle
  - OLAP: ClickHouse (колонночная аналитика), Snowflake/BigQuery (если облако)

### 1.1.* Хеширование стало занимать длительное время — какое API использовать?

Если речь про хеширование паролей/секретов или тяжёлые крипто-операции в приложении, то можно использовать нативные крипто-API языка/ОС, которые задействуют оптимизированные реализации и иногда аппаратные ускорения:
 - OpenSSL (libcrypto/EVP API) - де-факто стандарт в C/C++ и через биндинги в других языках
 - Java: JCA/JCE (MessageDigest, SecretKeyFactory, PBKDF2/BCrypt/SCrypt/Argon2 через провайдеры)
 - .NET: System.Security.Cryptography

В случае с обработкой паролей важно не ускорять любой ценой
Алгоритмы вроде bcrypt/argon2 специально медленные
Ускорять можно за счёт:
 - правильных параметров cost,
 - параллелизма (очередь задач/worker pool),
 - аппаратных возможностей, но без потери безопасности.

### 1.2. Под каждый девелоперский проект создаётся отдельный лендинг, и все данные по лидам стекаются в CRM к маркетологам и менеджерам по продажам. Какой тип СУБД лучше использовать для лендингов и для CRM? СУБД должны быть гибкими и быстрыми.

В данной ситуации 2 разных профиля нагрузки:

 - Лендинги:
    Часто это простые формы, сессионные данные, события, пиксели
    Поэтому будет удобно использовать NoSQL key-value/document.
    Пример: Redis (как быстрая KV/кэш/сессии) в совокупности с документной (MongoDB) для событий/форм.

 - CRM:
    Обычно задействованы сложные связи: лид-> сделки-> контакты-> активности-> статусы-> воронки-> права-> история изменений.
    Лучше использовать SQL (OLTP): строгая схема, транзакции, уникальности, ограничения, отчёты по менеджерам/воронкам.

Итого:
  Лендинги: Redis/MongoDB (или PostgreSQL, если всё просто).
  CRM: PostgreSQL/MS SQL/Oracle.

### 1.2.* Можно ли эту задачу закрыть одной СУБД? И если да, то какой именно СУБД и какой реализацией?

Да можно, если выбрать “универсальную” SQL, чаще всего PostgreSQL:
 - Для лендингов: JSONB для гибких полей, плюс обычные таблицы, плюс индексы.
 - Для CRM: классическая реляционная модель.
 - Для скорости: кэш (Redis) можно подключить как слой, но формально хранилище будет одно.

Если необходима именно одна СУБД и распределённость/масштаб, то можно рассмотреть вариант с использованием NewSQL, но это обычно избыточно для типового варианта CRM+лендинг.

### 1.3. Отдел контроля качества решил создать базу по корпоративным нормам и правилам, обучающему материалу и так далее, сформированную согласно структуре компании. СУБД должна иметь простую и понятную структуру.

В данной ситуации важны: иерархия, версии документов, поиск, теги, права доступа.
Варианты:
 - Если это структурированная библиотека документов, то: SQL (простая и понятная схема: разделы-> документы-> версии-> вложения).
 - Если много текста и нужен умный поиск, то: SQL + поисковый движок (Elasticsearch/OpenSearch), как вторичный индекс.
 
### 1.3.* Можно ли под эту задачу использовать уже существующую СУБД из задач выше и если да, то как лучше это реализовать?

Да, можно.
Самый практичный вариант - положить это в ту же SQL (например, PostgreSQL), что и CRM/бюджетирование, но необходимо соблюсти ряд правил:
 - отдельная схема/база,
 - таблицы документов + таблицы иерархии (adjacency list или nested set),
 - полнотекстовый поиск (в PostgreSQL есть tsvector/tsquery) или внешний поисковик, если контента очень много.

### 1.4. Департамент логистики нуждается в решении задач по быстрому формированию маршрутов доставки материалов по объектам и распределению курьеров по маршрутам с доставкой документов. СУБД должна уметь быстро работать со связями.

В данном случае мы имеем два слоя:
 - Операционные данные (заказы, курьеры, статусы, окна доставки) - часто достаточно SQL.
 - Связи/граф и оптимизация маршрутов:

Если действительно много запросов по связям типа "найти кратчайший путь/оптимальный маршрут", то удобно использовать графовую СУБД: Neo4j/JanusGraph.
Либо PostgreSQL + PostGIS + pgRouting: в реальных компаниях это часто самый прагматичный путь (геоданные + маршрутизация рядом с SQL).
Маршруты и "кто и куда может поехать" - это графовые задачи + гео.

### 1.4.* Можно ли к этой СУБД подключить отдел закупок или для них лучше сформировать свою СУБД в связке с СУБД логистов?

Для отдела закупок обычно нужны: договоры, счета, номенклатура, остатки, согласования-> это SQL-контур.
Логистике нужен граф/гео-контур.

Поэтому лучшим вариантом будет:
 - единый SQL-источник для мастер-данных (номенклатура, поставщики, заявки, статусы),
 - логистика использует либо отдельную графовую/гео-БД, либо расширения в той же SQL,
 - интеграция через события/ETL (чтобы закупки не ломали логистические модели).

### 1.5.* Можно ли все перечисленные выше задачи решить, используя одну СУБД? Если да, то какую именно?

Теоретически все задачи можно реализовать в одной универсальной СУБД, например PostgreSQL, за счёт поддержки транзакций, JSONB, полнотекстового поиска, геоданных и расширений.

Однако на практике разные типы нагрузок (OLTP, OLAP, графовые запросы) требуют разных моделей хранения и оптимизаций.
Поэтому в промышленной архитектуре обычно применяют полиглотный подход, используя специализированные СУБД для аналитики, графов и поиска, а PostgreSQL оставляют как основную транзакционную систему.

### Задание 2

## Транзакции

### 2.1. Пользователь пополняет баланс счёта телефона, распишите пошагово, какие действия должны произойти для того, чтобы транзакция завершилась успешно. Ориентируйтесь на шесть действий.

Распишем 6 шагов успешной транзакции:
 1. Создание платежа: пользователь вводит номер и сумму-> система создаёт платёж в статусе created и валидирует данные (формат номера, лимиты, доступность услуги).
 2. Авторизация/резервирование средств: запрос в платёжный шлюз-> authorise/hold суммы на счёте.
 3. Запись в БД транзакции: фиксируется попытка платежа (idempotency key, чтобы не списать дважды), статус authorised.
 4. Вызов биллинга оператора: запрос к оператору на пополнение (с тем же id транзакции).
 5. Коммит/списание: если оператор подтвердил пополнение — делаем capture (окончательное списание) и меняем статус на success.
 6. Пост-обработка: выдаётся чек/квитанция, отправляется уведомление, производится запись в лог, обновлются отчёты.

Важным моментом во всей цепочке является идемпотентность и согласованность статусов между банком, нашим сервисом и оператором.

### 2.1.* Какие действия должны произойти, если пополнение счёта телефона происходило бы через автоплатёж?

В случае с автоплатежом мы получаем дополнительные шаги.
Добавляются шаги до начала транзакции:
 - Предварительное согласие: пользователь один раз подтверждает автосписания, сохраняется токен/привязка (без хранения реквизитов карты в нашем контуре).
 - Триггер: по расписанию или по условию (баланс ниже порога/дата месяца).

Дальше процесс идентичен, но с некоторыми изменениями:
 - вместо ввода карты - charge по токену,
 - если отказ/недостаточно средств - повторы по правилам и уведомления,
 - важно не "зациклить" платежи, следовательно установить лимиты на количество попыток и суммы.

### Задание 3

## SQL vs NoSQL

### 3.1. Напишите пять преимуществ SQL-систем по отношению к NoSQL.

1. ACID-транзакции (надёжная целостность при конкурентных изменениях).
2. Ссылочная целостность и ограничения (FK, UNIQUE, CHECK).
3. Мощный стандартный язык запросов SQL (JOIN, агрегаты, оконные функции).
4. Зрелые инструменты аналитики и отчётности (BI, ORM, оптимизаторы, планы запросов).
5. Предсказуемая модель данных (при наличии строгой схемы проще сопровождение, контроль версий схемы, аудит).

### 3.1.* Какие, на ваш взгляд, преимущества у NewSQL систем перед SQL и NoSQL.

Если смотреть глобально, то NewSQL обычно пытается дать:
 - как у SQL: реляционность + транзакции + SQL интерфейс,
 - как у NoSQL: горизонтальное масштабирование и распределённость из коробки.

Преимущества:
 - Горизонтальное масштабирование OLTP без отказа от SQL/ACID.
 - Авто-шардинг/репликация, высокая доступность.
 - Часто сильная согласованность в распределённой среде (в отличие от eventual consistency во многих NoSQL).
 - Удобнее для систем, где и нагрузка большая, и транзакции критичны (финансы, биллинг).

Но также есть и минусы: сложность, цена, требования к сети/latency, иногда ограничения по фичам классических SQL.

### Задание 4

## Кластеры

Необходимо производить большое количество вычислений при работе с огромным количеством данных, под эту задачу выделено 1000 машин.

### На основе какого критерия будете выбирать тип СУБД и какая модель распределённых вычислений здесь справится лучше всего и почему?

Сначала рассмотрим критерии выбора типа СУБД.
Главное - характер нагрузки и модель доступа к данным:
 - OLTP (много мелких транзакций) vs OLAP (тяжёлые сканы/агрегации) vs граф/гео/вектор.
 - Требуемая согласованность (strong vs eventual).
 - Тип запросов: точечные по ключу, джойны, сканы по колонкам, ML-фичи и т.д.
 - Стоимость data movement: где будут выполняться вычисления - рядом с данными или в отдельном compute-слое.

Рассмотрим какая модель распределённых вычислений справится лучше:

Для массовых вычислений/ETL/агрегаций по огромным данным обычно лучше MPP (Massively Parallel Processing) или MapReduce/Spark-подход:
 - MPP (Greenplum/ClickHouse-кластер/другие MPP) хорош, когда основная работа - SQL-агрегации и аналитика: данные распределены, запрос распараллеливается, минимум лишних перегонов.
 - Spark/Flink хороши, когда вычисления сложнее чистого SQL (ML-пайплайны, графовые итерации, сложные трансформации), и нужен отдельный compute слой поверх хранилища (data lake).

Вывод:
Если это аналитика и расчёты в стиле SQL, то нужно использовать MPP-хранилище.
Если это сложные распределённые вычисления/ML/потоки, то лучше подойдёт Spark/Flink + хранилище (lake/warehouse).
